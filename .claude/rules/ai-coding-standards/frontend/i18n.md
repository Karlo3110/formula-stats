# Internationalization (Translations)

All user-facing text comes from translation files. **No hardcoded strings in components.**
This applies even to single-locale apps — it centralizes copy and makes adding locales free.

## Library

Use `next-intl` for the Next.js App Router (server- and client-component aware). The rules
below are library-agnostic and hold regardless.

## Folder structure

```
src/
└── translations/
    ├── en.json
    ├── hr.json
    └── ...
```

For larger apps, split each locale into namespaces by feature:

```
src/translations/
├── en/
│   ├── common.json
│   ├── auth.json
│   └── dashboard.json
└── hr/
    ├── common.json
    ├── auth.json
    └── dashboard.json
```

## Key naming (deterministic)

`<namespace>.<area>.<element>` — nested, descriptive, stable.

```json
{
  "auth": {
    "login": {
      "title": "Sign in",
      "emailLabel": "Email",
      "submit": "Sign in",
      "error": {
        "invalidCredentials": "Email or password is incorrect."
      }
    }
  }
}
```

Rules:
- Keys describe location and purpose, never the English text (`auth.login.submit`, not
  `signInButton`).
- The same key exists in every locale file. A missing key fails CI (use a checker).
- No string concatenation to build sentences; use interpolation and pluralization features.

## Usage

```tsx
import { useTranslations } from "next-intl";

export function LoginForm(): JSX.Element {
  const t = useTranslations("auth.login");
  return (
    <form>
      <Label>{t("emailLabel")}</Label>
      <Button>{t("submit")}</Button>
    </form>
  );
}
```

- Components reference keys only; they never contain literal user-facing copy.
- Interpolation and plurals use the library's mechanism, not manual string building:

```json
{ "cart": { "itemCount": "{count, plural, =0 {No items} one {# item} other {# items}}" } }
```

## Formatting

- Dates, numbers, and currency are formatted through the i18n/`Intl` layer with the active
  locale — never hand-formatted. See the date utility in `frontend/routing-layouts-guards.md`
  and `Intl.DateTimeFormat`/`Intl.NumberFormat`.

## Routing and locale

- Locale is part of the routing strategy (e.g. `/[locale]/...` segment) or negotiated from
  the request. Decide at project start and keep it consistent.
- The default locale and supported locales come from a single config constant.

## What must be translated

- All visible UI copy, validation messages shown to users, emails, and notifications.
- Not translated: log messages, internal error codes, identifiers, and developer-facing text.
